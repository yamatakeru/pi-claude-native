# The provider states what it knows; Pi decides retries

Pi's auto-retry decides from the error text alone. Its classifier first checks patterns it never retries, such as `billing`, then patterns it retries. The text is the only channel: `AssistantMessage` has no retryability field, `diagnostics` are not read, and extensions get no hook before a retry. Compaction and branch summaries retry through pi-ai's `retryAssistantCall`, which does not pass through `message_end`. #99 kept failures after the request was sent out of Pi's retries, because Anthropic may already be processing them. That rule relied on Pi not matching the text. Pi 1.6.0 retries bare socket codes such as `ECONNRESET` and `ETIMEDOUT` ([earendil-works/pi#12128](https://github.com/earendil-works/pi/issues/12128)), and the relay's failure text names them, so the rule no longer held (#106).

## Decision

- **The provider states facts Pi cannot know, in its classifier's vocabulary, and leaves policy to Pi.** The unsent note (`[upstream connect failed before the request was sent]`) says nothing reached Anthropic, so Pi retries it, also on Pi before 1.6.0 and for codes Pi does not list. A usage-credit error says `billing`, so Pi never retries it.
- **Failures after the request was sent get no mark.** Pi's classifier already has a policy for this kind of failure: it retries a reply dropped after it began (`cut short after the reply had begun`, `stream ended before message_stop`, `terminated`) for every provider. The relay knows the phase as well, but that does not change what a duplicate costs, which is the same kind of cost as with any provider. Whether to accept it is the user's policy, set with Pi's auto-retry.
- **Marks are set in the provider**, where every call runs, including compaction, branch summaries, and side requests from other extensions. Upstream failures are worded in the completion gate (`src/completion.ts`). Claude Code timeouts are raised earlier, in the child supervisor (`src/process.ts`), so a mark on every post-send failure would have to cover both.
- **A structured retryability field in Pi would replace text matching.** It is not requested; Claude Native adopts it if Pi adds one.

## Considered options

- **Stopping post-send auto-retries, the #99 rule, with a non-retryable note.** A note starting with `billing:` that says the request may count against the plan twice would work like the unsent note in reverse. With such a note, texts containing `ETIMEDOUT`, `ECONNRESET`, `timed out`, or `Connection error.` were non-retryable under both Pi 1.5.2 and 1.6.0. Not the default: unattended runs, such as subagents, would fail on a transient drop, as the four failures behind #99 did, and a manual retry duplicates the request just the same. Automatic retries add at most three attempts. It could later become an opt-in environment variable covering every post-send failure, including the timeouts #100 keeps retryable. Not built.
- **Removing the Node code so Pi's patterns do not match.** This hides the cause from the user and relies on what Pi does not match, which a Pi release can change at any time, as 1.6.0 did. Rejected.
- **Retrying resets before the response and stopping failures after it started.** The relay cannot tell who reset the connection. In the [measurements](../transport-measurements.md#whether-anthropic-processes-a-request-whose-connection-broke-106), the same `ECONNRESET during request` came from a request Anthropic processed and from one it did not. Rejected.
- **Setting the mark in a `message_end` handler, from the provider's diagnostic.** Compaction, branch summaries, and side requests would bypass it, and it depends on Pi replacing the message before its retry decision, checked only in Pi 1.6.0. Rejected.
- **Matching Pi's built-in Anthropic provider**, which also retried these failures in Pi 1.5.2. That provider knows only the SDK's error text, less than the relay does, so matching it is not a reason by itself. The first version of this ADR rested on it; the decision above replaces that reasoning without changing the behavior.

## Consequences

- A post-send retry can use plan allowance twice. At Pi's defaults (3 retries), one turn makes at most 4 attempts. Each attempt sends one upstream request, or two when the first is answered with a 401 authentication error, so a turn sends at most 8. Against a loopback upstream that reset every request, a turn sent 4. Users who want no such retries turn off Pi's auto-retry, which applies to every provider.
- A retry cannot run a tool twice. Tool calls are published only after a complete response, and Pi leaves the failed attempt out of the retried request. A loopback upstream that sent a complete `tool_use` block and then reset confirmed that no tool ran.
- In the measured cases, Anthropic processed a request whose connection failed silently or closed after the response started, so the retry duplicated it, reading the input from the cache. When Anthropic saw the close before the response started, no retry found the request's input in the cache, even 22 seconds later. Whether plan usage counts these requests is not verified ([measurements](../transport-measurements.md#whether-anthropic-processes-a-request-whose-connection-broke-106)).
